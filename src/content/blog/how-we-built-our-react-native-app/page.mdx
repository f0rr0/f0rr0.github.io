After [launching our PWA](https://medium.com/engineering-housing/progressing-mobile-web-fac3efb8b454), we wanted to bring the same experience to Housing's mobile apps. The web work had focused on slow, inconsistent connections. The next problem was keeping that work from turning into three separate versions of every product decision.

We had Android, iOS and web experiences spread across four codebases. A feature could mean several implementations, several rounds of fixes, and several opportunities for the platforms to drift apart. We wanted our web engineers to be able to work on the apps too, without making the apps feel like websites wearing a different coat.

React Native gave us somewhere to start. This was 2017; plenty of its conventions were still being worked out. We picked a stack our team could reason about and began learning where shared JavaScript helped—and where the device wanted our attention.

## Give each piece a place

We separated UI components from stateful views, and kept state changes in reducers and [redux-observable](https://redux-observable.js.org/) epics. Navigation lived in Redux too, through the early JavaScript-based [react-navigation](https://reactnavigation.org/).

That arrangement came partly from old bruises. Mutations in reducers had caused difficult bugs on our previous platforms, so we used immutable data structures for app state. Side effects scattered through component lifecycle methods had also made code harder to follow and test. Epics gave requests and their consequences a place of their own.

Persistence became another part of that state model. We used [redux-persist](https://github.com/rt2zz/redux-persist) with migrations and AsyncStorage so the app could carry state between sessions as it changed across releases.

For the interface, Storybook let us build components in isolation and map them to the design guide. This was one of the satisfying parts: the design could become a set of actual components we used on both platforms.

![Housing's shared style guide across Android and iOS](./styleguide.png)

More than 90% of the app's source ended up in JavaScript. Getting it to feel comfortable on a phone, though, required paying attention to when that JavaScript ran.

## Let the ripple happen

A button could work and still feel wrong. On Android, an expensive `onPress` handler sometimes prevented the touch ripple from appearing. Giving the animation a frame with `requestAnimationFrame` before doing the work made the response visible again.

The same issue showed up at a larger scale with screen transitions. `InteractionManager` let us defer expensive JavaScript until an interaction had finished. We could keep the transition moving and do the work afterward.

When we needed to see what was crossing between JavaScript and native code, the bridge had a wonderfully direct debugging switch:

```js
MessageQueue.spy(true);
```

Watching that traffic made it easier to connect the code we had written to the work happening on the device. In a couple of places we used `setNativeProps` to update a native view directly, after the normal render path hadn't worked well enough. Most of the time, scheduling the work sensibly was the more useful place to begin.

## Keep the request out of the component

Locality autocomplete was a good example of why we wanted side effects in one place. Typing creates a stream of requests, and by the time an old one finishes, the user may already be asking for something else.

Our epic kept the wait, request, retry and result together:

```js
export default function localitySelect(action$, store, { ajax }) {
  return action$
    .ofType('LOCALITY_AUTOCOMPLETE')
    .debounceTime(150)
    .distinctUntilChanged()
    .switchMap(({ payload: { text, cursor } }) => {
      return ajax
        .getJSON(
          `${api.searchSuggest}&cursor=${cursor}&string=${text}`
        )
        .retry(3)
        .map(({ response }) => ({
          type: 'LOCALITY_SUGGEST',
          payload: { data: response }
        }))
        .catch(error =>
          Observable.of({
            type: 'LOCALITY_SUGGEST',
            payload: { error },
            error: true
          })
        )
    })
}
```

`debounceTime` waited for a pause in typing. `switchMap` switched to the newest request as input arrived. The component didn't need to coordinate those steps through its lifecycle. We also passed `ajax` into the function, which let a test supply a replacement without making a real network request.

Navigation gave us another chance to take repeated work out of individual screens. Analytics, logging and the iOS status bar all needed to respond to route changes. With navigation in Redux, middleware could compare the route before and after an action:

```js
const statusBarMiddleware = ({ getState }) => next => (action) => {
  if (!Object.values(NavigationActions).includes(action.type)) {
    return next(action)
  }
  const currentScreen = getCurrentRouteName(getState().rootNavigation)
  const result = next(action)
  const nextScreen = getCurrentRouteName(getState().rootNavigation)
  if (nextScreen !== currentScreen && Platform.OS === 'ios') {
    setStyleForRoute(nextScreen)
  }
  return result
}
```

The status bar changed when the route did, and each screen had one less piece of housekeeping to remember.

## Get a build into somebody's hands

![Housing's React Native build and release pipeline](./pipeline.png)

Eventually a working app has to leave a developer's phone. For us, that meant signing, test devices, staging credentials, release notes and getting the build to QA. After trying several approaches, we put the release steps into Fastlane and exposed them through our Jenkins dashboard.

The useful change was where the pipeline lived: beside the application code. CI pulled a fresh checkout for each build, so changing a release step became an ordinary repository change. CodePush handled JavaScript updates, while Sentry brought native and JavaScript stack traces into the same error reports. Jest and Detox gave us checks below and above the interface.

That closed the loop we wanted at the start. Our web engineers could work on a shared application, see its components on both platforms, and get a build into testing. The last check was still on a real device. It was where a missing ripple could remind us that sharing the code was only part of making the app feel right.
